{% docs int_erp_integrations_overview %}
Ce document regroupe les spécifications d'interfaces ("INT") nécessaires pour alimenter l'entrepôt depuis l'ERP et les systèmes périphériques.

Chaque bloc ci-dessous décrit pour un domaine métier : le but de l'interface, le format attendu, la fréquence, le schéma attendu (champ/type), les règles de validation et suggestions pour le mapping vers les modèles de staging (`stg_erp__...`).

IMPORTANT : les coordonnées techniques (hôte SFTP, identifiants, endpoints API) sont des placeholders — adaptez-les à l'environnement de production.
{% enddocs %}

{% docs int_erp_purchases_suppliers %}
But : transmettre les commandes d'achat, lignes de commandes et données fournisseurs depuis l'ERP vers l'entrepôt afin d'alimenter analyses achats, délai fournisseur, et réconciliations factures/commandes.

Scénarios supportés :
- Chargement initial complet (full) puis envoi incrémental (delta) quotidien ou en quasi temps réel suivant disponibilité.
- Evénements : création / mise à jour / suppression logique (soft delete).

Format recommandé : JSON Lines (newline-delimited JSON) ou CSV (UTF-8). Chaque fichier contient un lot d'entités homogènes (orders / order_lines / suppliers / supplier_contacts).

Fréquence : quotidienne (00:30) pour delta ; full mensuel ou initial.

Schémas (exemples) :
- purchase_orders (fichier: purchase_orders_{YYYYMMDD}.jsonl)
  - id (string) PK
  - supplier_id (string)
  - reference (string)
  - status (string)
  - order_date (date)
  - delivery_date (date|null)
  - currency (string)
  - total_amount (decimal)
  - created_at (timestamp|null)
  - updated_at (timestamp|null)

- purchase_order_lines (fichier: purchase_order_lines_{YYYYMMDD}.jsonl)
  - id (string) PK
  - purchase_order_id (string) FK -> purchase_orders.id
  - line_number (int)
  - product_id (string)
  - qty_ordered (decimal)
  - unit_price (decimal)
  - tax_amount (decimal)
  - created_at (timestamp|null)
  - updated_at (timestamp|null)

- suppliers (fichier: suppliers_{YYYYMMDD}.jsonl)
  - id (string) PK
  - name (string)
  - code (string)
  - is_active (boolean)
  - created_at (timestamp|null)
  - updated_at (timestamp|null)

Validation / règles :
- Les identifiants (id) doivent être stables et uniques.
- Les lignes (`purchase_order_lines`) doivent référencer une commande existante (si ordre absent, stocker en file d'attente ou envoyer avec statut `orphan`).
- Format des dates : ISO 8601 (YYYY-MM-DD ou YYYY-MM-DDTHH:MM:SSZ).
- Montants décimaux : séparer la précision (ex : decimal(38,9)).

Erreurs et idempotence :
- Chaque fichier doit contenir un en-tête `batch_id` et `batch_timestamp` pour la traçabilité.
- Les payloads doivent être idempotents : envoyer la même ressource multiple fois ne doit pas créer de doublons si `id` identique.
- En cas d'erreur de validation, renvoyer un rapport `purchase_errors_{batch_id}.json` contenant les lignes rejetées avec la raison.

Mapping dbt : maps -> `stg_erp__purchase_orders`, `stg_erp__purchase_order_lines`, `stg_erp__suppliers`, `stg_erp__supplier_contacts`.
{% enddocs %}

{% docs int_erp_inventory %}
But : fournir les mouvements de stock, niveaux et ajustements pour suivre les quantités physiques, valorisation et écarts d'inventaire.

Scénarios supportés : transferts, ajustements manuels, comptages périodiques (cycle counts), réservations et consommations liées ordres de fabrication.

Format recommandé : JSON Lines ou CSV.
Fréquence : temps réel pour mouvements critiques ; batch horaire ou quotidien pour reporting.

Schémas (exemples) :
- inventory_counts
  - id (string) PK
  - warehouse_id (string)
  - reference (string)
  - status (string)
  - started_at (timestamp)
  - completed_at (timestamp|null)
  - validated_at (timestamp|null)
  - created_at (timestamp|null)

- inventory_count_lines
  - id (string) PK
  - inventory_count_id (string) FK
  - component_id (string)
  - counted_qty (decimal)
  - expected_qty (decimal)
  - variance (decimal)
  - counted_at (timestamp)
  - location_id (string|null)

- component_stock_movements
  - id (string) PK
  - component_id (string)
  - from_location_id (string|null)
  - to_location_id (string|null)
  - qty (decimal)
  - movement_type (string)
  - occurred_at (timestamp)

Validation / règles :
- Les mouvements doivent inclure `inventory_transaction_id` ou `reference` pour traçabilité.
- Les quantités doivent être positives ou négatives selon le sens ; la somme des mouvements pour une période doit correspondre à la variation réelle constatée.
- Les inventaires de clôture doivent indiquer `warehouse_id` et grain : 1 ligne par composant + emplacement.

Mapping dbt : maps -> `stg_erp__inventory_counts`, `stg_erp__inventory_count_lines`, `stg_erp__component_stock_movements`, `stg_erp__stock_levels`, `stg_erp__component_stock`.
{% enddocs %}

{% docs int_erp_sales_billing %}
But : alimenter les factures clients/fournisseurs, écritures de facturation et paiements pour le reporting chiffre d'affaires, comptes clients/fournisseurs et rapprochements.

Schémas (exemples) :
- vendor_invoices / customer_invoices
  - id (string) PK
  - reference (string)
  - partner_id (string) (supplier or customer)
  - invoice_date (date)
  - due_date (date|null)
  - amount_total (decimal)
  - currency (string)
  - status (string)
  - created_at (timestamp|null)
  - updated_at (timestamp|null)

- vendor_invoice_lines / customer_invoice_lines
  - id (string) PK
  - invoice_id (string) FK
  - product_id (string|null)
  - qty (decimal)
  - unit_price (decimal)

Validation / règles :
- Lignes d'invoices doivent totaliser `amount_total` (tolérance configurable).
- Dates en ISO 8601.

Mapping dbt : maps -> `stg_erp__vendor_invoices`, `stg_erp__vendor_invoice_lines`.
{% enddocs %}

  - first_name (string)
  - last_name (string)
  - email (string|null)
  - hired_at (date|null)
  - left_at (date|null)
  - is_active (boolean)

- timesheets
  - id (string) PK
  - employee_id (string) FK
  - week_start (date)
  - total_hours (decimal)
  - status (string)
  - created_at (timestamp|null)

- timesheet_lines
  - id (string) PK
  - timesheet_id (string) FK
  - day (date)
  - hours (decimal)

{% docs int_erp_accounting_finance %}
But : fournir écritures comptables, plan comptable, fiscalités et périodes pour la consolidation et reporting financier.

Schémas (exemples) :
- journal_entries
  - id (string) PK
  - journal_date (date)
  - period_id (string)
  - reference (string)
  - created_at (timestamp|null)

- journal_entry_lines
  - id (string) PK
  - journal_entry_id (string) FK
  - account_number (string)
  - debit (decimal)
  - credit (decimal)

- chart_of_accounts
  - account_number (string) PK
  - name (string)
  - type (string)

Validation / règles :

Mapping dbt : maps -> `stg_erp__journal_entries`, `stg_erp__journal_entry_lines`, `stg_erp__chart_of_accounts`, `stg_erp__fiscal_years`.
